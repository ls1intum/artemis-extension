    **4. Update ArtemisWebviewProvider.ts** for Login message bridging:

    The Login view is special because the extension host sends many messages to it (showLoading, hideLoading, loginSuccess, loginError, showLoggedIn, setServerUrl, logoutSuccess). These are currently sent in legacy `{ command: 'xxx' }` format.

    **Two approaches (choose the simpler one):**

    A. **Have LoginView handle legacy format** — The LoginView's message handler already listens for both `event.data.type` and `event.data.command` formats (specified in Task 1 action). This requires no changes to the provider.

    B. **Wrap provider messages for React views** — In provider methods that postMessage, check if current view is React and wrap accordingly.

    **Choose approach A** for simplicity: LoginView handles both formats. The extension host continues sending `{ command: 'showLoading', message: '...' }` and the React component handles it alongside the typed format.

    However, update the ready-signal handler:
    - When ready signal received and current state is 'login': send `{ type: 'setServerUrl', payload: { serverUrl: this._getServerUrl() } }` and then call `this._checkExistingAuthentication()` to trigger the auto-login flow (which sends showLoading -> showLoggedIn or hideLoading)
    - When state is 'login' and ready signal fires, the existing `_checkExistingAuthentication()` logic already runs in `resolveWebviewView()`. But with the React view, it may fire before the ready signal. So in `resolveWebviewView()`, move the `_checkExistingAuthentication()` call to happen AFTER the ready signal is received (inside the ready handler). For non-React views (legacy), keep calling it immediately as before.

    **Important consideration:** The login view is the default initial view. When the extension first activates, `resolveWebviewView` is called, which sets up the webview HTML and then checks auth. With React, the auth check messages (showLoading etc.) must be queued until ready. The `_postMessageSafe` method from Plan 01 handles this — messages sent before ready are queued and flushed when ready fires. So the existing `_checkExistingAuthentication()` flow (which calls `postMessage({ command: 'showLoading' })`) will be queued and delivered after React hydrates. This should work without moving the call.

    Verify this works by checking: after `webviewView.webview.html = ...` is set, `_checkExistingAuthentication()` runs and sends messages. Those messages go through `_postMessageSafe` which queues them. When React renders and sends `{ type: 'ready' }`, the queued messages are flushed. The LoginView receives them and displays loading state.

    **BUT:** The existing code uses `this._view.webview.postMessage()` directly in several places (showDashboard, showLogin, hideLoadingAndSendServerUrl, _checkExistingAuthentication). These bypass `_postMessageSafe`. Fix: update these to use `_postMessageSafe` when the current state maps to a React view. OR better: make `_postMessageSafe` the default message sending path, and have `_postMessageSafe` always check `_webviewReady` — for legacy views, `_webviewReady` should always be true (set immediately since legacy views don't send ready signal).

    **Simplification:** After Plan 01 establishes the ready-signal pattern, ALL postMessage calls from the provider should go through `_postMessageSafe`. For legacy views, set `_webviewReady = true` immediately after setting `webview.html` (since legacy views don't need the handshake). For React views, wait for the ready signal. This means: in `resolveWebviewView`, after `webviewView.webview.html = ...`, check if the current view is a React view. If not, set `_webviewReady = true` immediately.
