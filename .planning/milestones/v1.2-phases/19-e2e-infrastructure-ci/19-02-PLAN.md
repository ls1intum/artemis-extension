**Title:** ADR 001: E2E Test Framework Selection

**Date:** 2026-02-28

**Status:** Accepted

**Context section:**
- The extension requires E2E UI tests that launch a real VS Code instance and interact with Artemis webview panels
- The extension uses sidebar webview panels (not editor tabs) which limits framework options
- Three frameworks were evaluated during initial test architecture setup

**Options Considered — comparison table:**

| Framework | Version | Approach | Pros | Cons |
|-----------|---------|----------|------|------|
| vscode-extension-tester | v8.22.0 | Selenium WebDriver, launches real VS Code, provides WebviewView page object for sidebar iframe switching | Mature ecosystem, sidebar webview iframe support via `WebviewView.switchToFrame()`, existing helper library built (`switchToWebviewFrame`, `waitForElement`, `takeScreenshot`), screenshot-on-failure for debugging | Selenium-based (heavier than Playwright), no native CI runner (requires xvfb for Linux), flaky element waits |
| wdio-vscode-service | latest | WebDriverIO service for VS Code, extends wdio with VS Code-specific locators | Modern WebDriverIO ecosystem, good documentation, active maintenance | No sidebar webview iframe support — cannot switch into webview iframe context for sidebar panels. Blocking limitation for this extension's architecture. |
| Playwright | N/A | Browser automation framework with potential VS Code extension support | Fast, reliable, modern API, excellent debugging tools | No VS Code extension automation target (microsoft/playwright#22351 open). Cannot launch VS Code or interact with extension host. Entirely excluded — not a viable option. |

**Decision section:**
- Retain `vscode-extension-tester` v8.22.0
- The existing E2E helper library (`test/e2e/ui/helpers.ts`) provides sidebar webview switching, element waiting, credential management, and screenshot capture
- E2E tests run locally only (not in CI) via `npm run test:ui` / `run-tests.sh`
- wdio-vscode-service and Playwright are not evaluated further

**Consequences section:**
- E2E tests depend on Selenium WebDriver and ChromeDriver managed by vscode-extension-tester
- Tests require a running Artemis + Iris instance with valid credentials (env vars: ARTEMIS_USER, ARTEMIS_PASS)
- Screenshot-on-failure is available locally for debugging via `takeScreenshot()` helper
- CI runs unit (Vitest) and integration (Mocha) tests only — E2E remains local
- Future contributors should not introduce wdio-vscode-service or Playwright for E2E testing in this project
- If Playwright adds VS Code extension support (issue #22351), this decision should be revisited

Keep the ADR focused and concise. No broader test landscape overview needed (per CONTEXT.md decision). Do not include the sandwich testing architecture — that belongs in a separate document if needed.
